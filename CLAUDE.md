# Uddokta

Bangla-first commerce SaaS for Bangladeshi sellers who take orders through Facebook and cash on delivery. It covers the feature set in `winningseller-analysis.md`, with Shopify-style navigation, a polished minimal design and a media gallery for each store.

Use the analysis as a feature reference only. Write our own copy, guides and branding; never reuse WinningSeller's or Shopify's text, logos or assets.

## Stack (decided, do not change without asking)

| Layer | Choice |
|---|---|
| Language | TypeScript |
| Dashboard | React + Vite single-page app, React Router |
| API | Hono on Node.js |
| Storefront | Hono rendering React to HTML on the server, JavaScript only where needed (cart, checkout) |
| Page editor | Same React section components as the storefront |
| Database | Managed PostgreSQL + Drizzle |
| Background jobs | pg-boss |
| Media | Cloudflare R2, images resized at upload with sharp |
| CDN, store domains | Cloudflare (`uddokta.live` DNS, R2, CDN) |
| Sellers' own domains | One Caddy proxy on Fly.io with a fixed IPv4; on-demand certificates approved by our API, forwarded to the storefront |
| Hosting | Railway (app and Postgres). Its filesystem does not persist, so uploads never go on local disk in production |
| UI primitives | Radix + our own design tokens |
| Packages | npm workspaces |

**Do not use:** Next.js, Vercel, Polaris (its license is for Shopify apps), microservices, Kubernetes or Kafka.

**Add only when the need is measured:**
- Redis: repeated reads slow the database
- Read replicas: reports slow order processing
- ClickHouse: analytics queries get slow on Postgres
- Typesense: Postgres search fails, especially for Bangla
- Separate services: one part needs its own team or scaling profile

## Architecture rules

- Every tenant table has `store_id`, enforced with Postgres row-level security.
- API, storefront and workers are stateless and deploy separately.
- Storefront pages are cached at the CDN and purged when a seller publishes.
- Page views and ad events never share tables with orders.
- Money is calculated by the system, never by AI.
- Pages are versioned JSON, with draft and published states.
- Each section declares a settings schema, and the editor form is generated from it.

## Accounts and stores

- `users`, `stores` and `store_members (user_id, store_id, role)`: many-to-many. Roles are owner, admin and staff.
- A user can exist with no store. A store always has an owner: this is enforced by deferred triggers in the database, not only in code.
- Team members join through single-use invite links that last 7 days, sent by the owner (for example on WhatsApp). No email provider is needed.
- Dashboard URLs are `/store/:handle/...`. Screens outside a store (`/stores`, `/stores/new`, `/account`) use the account layout.
- Profile (`/account`, opened from the name and email row in the account menu; `apps/api/src/profile.ts`): name, email, password, devices, language, delete account. Changes go through definer functions (migration 0096) with the session's user; email change, password change and deletion ask for the current password again (wrong ones count like log in). Changing the password signs out every other device; so does "Sign out all other devices". A new email changes only when the link sent to it is used (24 hours), the old address gets a notice, and a password reset or signing out other devices cancels a pending change. `users.language` follows the dashboard language (synced in `AccountProvider`) and is the language of the account's emails. Deleting an account is refused (`soleOwner`, with the store names) while it is a store's only owner.
- Every API query goes through `tx()` in `apps/api/src/db.ts`, which drops to the restricted `uddokta_app` role and sets the user for one transaction. Never query outside it. New tenant tables need `store_id`, row-level security policies and a test proving another store cannot reach them.
- UI permission checks are only for display. The database and API are the real enforcement.
- Settings › Team shows what each role can do from `apps/dashboard/src/permissions.ts`. That list only explains the rules: when a role rule changes in the database or API, update it in the same change.

## Account email

- Password reset, email verification (and later other account email) go through `apps/api/src/email.ts`: `sendEmail` queues a row with `queue_email` inside the request and starts `drainOutbox`, which sends through Amazon SES (API v2 over HTTPS with `aws4fetch`, no SMTP) when `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` are set (`AWS_REGION`, default `ap-southeast-1`; `EMAIL_FROM`, default `Uddokta <no-reply@uddokta.co>`; optional `SES_CONFIGURATION_SET`). Without keys, development writes each email to `.emails/` (tests use `EMAIL_DIR`) and production sends nothing. Failures retry (1, 2, 4, 8 minutes, 5 tries) from a one-minute timer in `index.ts`; unsent emails are dropped after an hour (their links have expired). Sent bodies are cleared.
- Links point at `APP_URL` (the dashboard origin; `http://localhost:5173` in development), never at the request's host. Until both `APP_URL` and the SES keys are set in production (`emailReady`), nothing is sent: the verification bar is hidden (`/me` reports verified) and `/auth/forgot` answers 503 `emailUnavailable` instead of promising a link.
- `account_tokens`, `outbox_emails` and `email_suppressions` have no grants: only the definer functions in migration 0095 reach them (a test proves it). Tokens are random, stored as sha256, single use. Reset: 30 minutes, 3 an hour per account, `/auth/forgot` answers the same whether or not the email has an account, using the link sets the password, ends every session and marks the email verified. Verification: 7 days, sent at sign-up, resent from the dashboard bar (`VerifyEmailBar`), 3 an hour. Nothing is blocked for unverified accounts yet.
- SES reports permanent bounces and complaints to an SNS topic that posts to `/api/ses/events` (registered before the CSRF check). Only messages signed by SNS from `SES_EVENTS_TOPIC_ARN` are accepted; the addresses go into `email_suppressions` and get nothing again. Our SES production-access request promised this, so keep it working.
- Every email is a Bangla/English pair in `email.ts`, in the language the dashboard was using.

## Platform console (super administrators)

- Its own app and Railway service: `apps/console` (Hono server in `server/`, React screens in `src/`, `deploy/Dockerfile.console`, domain `console.uddokta.co`; development: screens on port 5174, server on 8789). The main API has no console routes. The console reuses the dashboard's styles and `components/ui.tsx`, and is in English (internal tool).
- Access: platform administrators are rows in `platform_admins`, added only from the server command line (`npm run admin -w console -- add|remove|list <email>`), never from the web. The console signs in on its own (`console_sid` cookie, Strict, 12-hour sessions); `console_session()` admits only an unsuspended administrator signed in within 12 hours. Anyone else, even a seller with their right password, gets the same `invalidCredentials` as a wrong password, counted towards the lockout.
- Every read and change goes through the `console_*` definer functions (migration 0097). Each one checks the administrator again (`console_check`) and writes `console_audit` itself; the app role has no grant on `platform_admins`, `plans`, `store_payments` or `console_audit` (a test proves it). Changes that affect people require a reason, kept in the audit log, which cannot be edited from the app.
- Screens: Overview (real counts, sign-ups chart, stores per plan), Users (search; suspend/restore, sign out everywhere, send the normal reset link: the console never sees or sets passwords), Stores (search; plan, limits and usage, team, payments; change plan, record payment, suspend/restore), Plans, Audit log. No "log in as" in version 1.
- Plans are per store (`plans`, `stores.plan_id`, `stores.plan_until`). `store_limits()` gives a store's plan now: its own while paid or with no end date, else the default plan (exactly one, never archived; starts as Free with the old fixed limits). A null limit is unlimited. Limits are enforced in the API through `storeLimits` (`apps/api/src/plans.ts`): landing pages (`pageLimit`), products (`productLimit`), team members plus open invites (`memberLimit`), media storage (`storageFull`), own domain (`planNoDomain`). Payments are recorded by hand (bKash, Nagad, bank) with `console_record_payment`, which extends the plan from today or its current end date.
- Managing plans (migration 0106): a `hidden` plan is left off sellers' Billing page (an early-access or by-invitation plan) but can still be the default or be given from a store's page; stores on it still see it as their plan. Archived plans can no longer be given; stores already on one keep it until moved. `console_move_plan_stores` moves every store set to a plan onto another (or the default plan, with no end date; reason required). `console_delete_plan` removes a plan only when it is not the default, no store is set to it and no payment was recorded on it (409 `planHasStores` / `planHasPayments`); otherwise archive it. Stores with no plan of their own follow the default, so changing the default moves them.
- Plan tools: `planFeatures` in `apps/storefront/src/plans.ts` (online store, own domain, courier booking, discounts, fake-order protection, incomplete orders, repeat sales, analytics, ad tracking; landing pages, orders, products and media are in every plan) with Bangla/English names. `plans.features` holds the keys (a check refuses unknown ones). The API closes a tool's routes, reading included, with 403 `planFeature:<key>` (`featureRoutes` in `guardStores`, `apps/api/src/plans.ts`; Steadfast booking checks `requireFeature` in `couriers.ts`); online store templates, Site settings and the store preview stay open because landing pages use them. Without `onlineStore` the storefront answers 404 for home, catalog, cart, search, buyer accounts, policies and store pages (`storefront_store_state`), and landing pages keep selling. The dashboard marks closed tools with a lock (`nav.ts` `feature`, `components/Plan.tsx`) and `PlanGate` explains them; it never decides access. A new tool needs its key, both names, its routes in `featureRoutes` and its screens wrapped. Every paid plan (price above ৳0, public or custom) includes `customDomain`: the database refuses one without it (`plans_paid_domain`, migration 0100), the console API adds it, and the console's checklist shows it ticked and locked; only free plans may leave it out.
- Custom plans: a plan row with `store_id` is that store's own (one per store, never default, not listed in Plans or offered to others), made and changed on the store's console page with the same limits and tool checklist plus an agreed price and a billing note shown to the store (`console_save_custom_plan`; ending it, `console_end_custom_plan`, returns the store to the default plan). Payments can be recorded against it like any plan.
- Settings › Billing (`pages/Billing.tsx`, `GET /stores/:handle/billing` via `store_billing()`, owners and admins only): current plan with status, usage tiles, included tools (missing ones locked), public plans as cards (Choose / Renew; hidden and archived plans are left out), three payment steps (plan and months with the total shown, bKash/Nagad/bank with copy buttons and the store address as reference, then a WhatsApp message prefilled with store, plan, months and amount; `platform_settings` edited on the console's Settings page) and recorded payments. The full comparison is the marketing site's pricing page (`uddokta.co/pricing`, `/en/pricing`; repository `uddokta-studio`, plans in `src/pricing.ts`, kept in step with the console's public plans by hand). Sellers do not change plans themselves yet: they pay and Uddokta records it.
- Store deletion (`apps/api/src/store-deletion.ts`, migration 0104): the owner asks from Settings › Store (`DeleteStoreSection`), typing the store address and their password (`confirmPassword`, wrong tries count like log in). `store_request_deletion` sets `deletion_due_at` 30 days ahead: the storefront treats it as closed (`storefront_store_state`), the API refuses changes with 423 `storeDeleting` (except `DELETE /stores/:handle/deletion`, the owner's restore), and every member sees `DeletionBar`. `sweepDeletedStores` (hourly from `index.ts`, `store_purge_due`) removes due stores: the store row (every tenant table cascades) and its media files. The console shows "Deleting" on Stores and the store page, can Export data (`console_export_store`: every table with a `store_id`, minus columns named like password/token/secret/credential/api_key/hash, with a reason in the audit log) and Delete now (`console_delete_store_now`, only while the owner's request stands). No refunds; nothing is kept. Platform columns of `stores` (suspension, plan, deletion) change only through definer functions: the `stores_platform_columns` trigger refuses them from the app role.
- Suspension: a suspended user has no live session (`session_owner`) and log in answers `accountSuspended` only after the right password. A suspended store answers 503 "unavailable" on every storefront page and post, and the API refuses its changes (`storeSuspended`, `guardSuspendedStores`) while the team can still read. Every store screen shows the team `SuspendedBar` (from `suspendedAt` in `/me`); the console's reason is never shown to sellers. "Contact support" places use `SupportLink` (`components/Support.tsx`, open `GET /support`: the WhatsApp number from the console's Settings); add it wherever new copy tells people to contact support.

## Development

- `npm run db:start`, then `npm run db:migrate`, then `npm run dev` (dashboard on port 5173, API on 8787, storefront on 8788 at `http://{store}.localhost:8788`, console on 5174 with its server on 8789, Postgres on 5433).
- `npm run db:pull-live` copies the live database into the local one (`scripts/pull-live.sh`; needs `LIVE_DATABASE_URL` in the git-ignored `apps/api/.env.live` and the live server's Postgres tools from Homebrew). It backs up local data to `~/uddokta-backups` first, deletes the live dump after loading, and clears sessions, email links and the outbox. It copies rows, not image files: with `LIVE_MEDIA_URL` set in `apps/api/.env` (development only), images missing from `.media/` redirect to the live bucket's public address (`liveMediaUrl` in `storage.ts`). Never point local development at the live database itself.
- `npm test` runs API tests against the `uddokta_test` database. `npm run build` type-checks both apps and builds the dashboard.
- Schema changes: edit `apps/api/src/schema.ts`, then `npm run db:generate -w api`. Row-level security and triggers go in custom migrations.
- For small UI changes, run the build and check the affected screen. Do not run long full-app browser tests unless the change is broad.

## Store customization

1. Style presets: one click sets colours, fonts and corners.
2. Section editor: add, drag and configure sections with a live preview.
3. Page fonts (`content.fonts`: a Bangla and an English font from the fixed Google Fonts list `pageFonts` in `themes.ts`; blank keeps the theme's; applied to `.sf-page` by `pageFontCss`). Per-element fonts may come later.
4. Custom CSS per landing page (`content.css`, in the editor's Page settings). `readContent` refuses `<` and more than 20,000 characters so it can never leave its `<style>` tag. Plan limits come with billing. No Liquid-style theme language.

The page editor's top bar has back, then icon toggles for the sidebar (Sections: list plus the selected section's settings; Page settings: full height, including Custom CSS in a lazy-loaded CodeMirror editor, `components/CssEditor.tsx`; Custom HTML blocks use `HtmlEditor.tsx`, both built on `CodeEditor.tsx`, with a Format code button that lazy-loads js-beautify), with the title and status centred. On phones the top bar is one line (back, title, status, view live, Save, Publish) and a bottom dock of equal tabs holds Page settings, Undo, Redo, Sections and Preview; tapping a section opens its settings and closing them returns to the list.

## Media gallery

Files live in Cloudflare R2 (`.media/` in development), and the `media` table holds their details. Never store uploads in the repo. The API converts every image to WebP, strips its metadata and makes a thumbnail.

One picker used across products, pages, templates and the logo. It shows where each file is used, blocks deleting a file that is live, compresses images automatically and counts against a per-plan storage limit.

## Products

- Every product has at least one variant, so price and stock always live on `product_variants`. Options generate one variant per combination, up to 100.
- Amounts are whole taka in integer columns. Blank stock everywhere means it is not tracked.
- Buying prices live in `product_variant_costs`, which row-level security hides from staff. Staff saves leave the field out and keep the existing price.
- Staff can add and edit products; only owners and admins can delete them.
- Statuses: active (listed and on sale), unlisted (on sale through its direct link, never in listings or search), draft (hidden). The storefront must honour all three.
- Descriptions and layout Text elements are rich text. `cleanRichText` in `apps/storefront/src/rich.ts` allows a few tags with no attributes, plus links with an http, https, mailto or tel `href`, and it is the only thing that makes them safe to render. The API runs it on save (`cleanDescription`, and `readContent` for `richtext` fields); the layout renderer runs it again before drawing, so the editor preview is safe too.
- Each product has a `handle`, unique in its store and allowed to contain Bangla. Saves keep it when the name changes. A blank search title or description means the storefront uses the name and `searchDescription` from `apps/dashboard/src/product-form.ts`.
- A variant image must be one of its product's images, enforced by a deferred foreign key to `product_media`.
- `product_media` has a deferred foreign key to `media`, which is what blocks deleting an image in use.
- Import (Products › Import): the Shopify or WooCommerce product CSV is read in the dashboard (`product-import.ts`) and sent one product at a time through the normal product API, best effort (what cannot map is blanked or skipped with a reason, the seller fixes it by hand; an existing address is skipped, so re-running continues). Images come through `POST /stores/:handle/media/import`, whose `downloadImage` (`images.ts`) refuses private networks, odd ports and other schemes; keep that guard on any new server-side fetch of a seller-given address.

## Attributes and store filters

- Attributes are facts about a product that are not buyer choices (origin, shelf life, certified). They are defined once per store (`attributes`, Products › Attributes) so every product uses the same names and values; that is what makes filters and search work. Kinds: `choice` (one or more of `attribute_choices`; renaming a choice renames it everywhere), `number` (with a unit, `numeric(12,3)`) and `flag` (yes/no). The kind never changes after creation. Each attribute says whether it shows on product pages and whether it is a store filter. Up to 50 per store, 100 choices each.
- Values are rows in `product_attribute_values` (one per choice, or one number/flag), saved with the product (`attributes` in the product body; left out keeps them). Composite foreign keys keep a value on its own store's product and a choice on its own attribute; the API checks the kind. Deleting an attribute or a choice removes its values (cascade); the dashboard says how many products it affects first. Staff add and edit; owners and admins delete (row-level security, like collections).
- Storefront: `storefront_product_attributes` feeds the product page table (Product details block setting, and the Product attributes block). Collection, all-products and search lists filter by price, stock and filterable attributes: `storefront_filter_rows` returns the listed products with their values (up to 2000), `filters.ts` reads the address, filters (any-of within an attribute, all-of across) and counts each attribute without its own filter, `storefront_cards` draws the page. The address is readable and shareable (`?উৎস=সুন্দরবন&min.মেয়াদ=6&max.price=1000&stock=1`), so attribute names may not be `page`, `q`, `stock`, `sort` or start with `min.`, `max.`, `price.` (`isAttributeName`). The panel is a plain GET form; `filterScript` only applies changes at once. Product list and search blocks have a Filters setting. Search (`storefront_matches`) also matches attribute choices and variant option values.

## Inventory

- One list of every variant, with stock edited in place, one warehouse at a time, and saved together. There is no stock history.
- Stock lives in `warehouse_stock`, one row per variant per warehouse. No rows means not tracked. A trigger keeps `product_variants.stock` equal to the total, so read that column for totals and never write it. Change stock through `setStock` in `apps/api/src/stock.ts`.
- Every store has at least one warehouse, made with the store, and the API refuses to delete the last. Deleting a warehouse moves its stock to another.
- Orders must change stock by adding or subtracting in the database, never by writing back a number read earlier, and must say which warehouse a sale ships from.
- The inventory list also edits SKU, barcode and the low-stock alert (`product_variants.low_stock`, compared with the total). "In orders" counts units on unshipped orders, which are already taken out of stock.

## Collections

- Sellers pick a collection's products by hand and drag them into order. Automatic rules (by tag, price) come later if sellers ask.
- A collection has no status of its own. The storefront shows only its active products, so unlisted and draft ones stay hidden even when they are in a collection.
- Staff can add and edit collections; only owners and admins can delete them. Deleting one never deletes its products.

## Landing pages

- `pages` holds a `draft` and a `published` JSON copy, plus `published_meta` for the public title, handle and SEO fields. Draft metadata never changes a live page; publishing snapshots it with the content. Live and draft handles share a store-scoped reservation namespace. Saving changes only the draft; Publish copies it. Saves send `revision`, and a stale one gets 409 `pageChanged` instead of overwriting.
- Sections live in `apps/storefront`: `schema.ts` (settings schemas, `readContent` validation, no JSX so the API imports it) and `sections.tsx` (stateless components). The storefront renders them to HTML; the editor renders the same components into an iframe preview. The editor's forms are generated from the schemas.
- Page content is version 2 only (`readContent` refuses anything else). A page is a list of sections: built-in typed sections, plus `layout` sections that hold a tree of nodes (`PageNode` in `schema.ts`): boxes (flex or grid containers, nestable at most 4 boxes deep (`maxBoxDepth`, enforced by `readContent` and checked in the editor before adding, pasting, dropping or growing a grid), max 400 nodes a page) and elements (heading, text, image, button, icon, divider, spacer, video, and `block`, which embeds any built-in section such as the order form inside a layout). Each node has content (`props`), desktop `style`, `hover` (Style-tab values only, edited with the Normal/Hover switch, falling back to the normal look like phone values fall back to desktop; rendered last inside `@media (hover:hover)`, and drawn in the editor preview while being edited) (borders are one width per side, `border{Top,Right,Bottom,Left}Width`, plus `borderStyle` solid/dashed/dotted; the older all-sides `borderWidth` still renders and is split up on the first edit; corners likewise are `radius{TopLeft,TopRight,BottomRight,BottomLeft}` over the older `radius`), phone overrides (`mobile`, under 720px) and `hide`. Style values come from the fixed list `nodeStyleFields`, so `layout.tsx` turns them into one generated stylesheet without escaping. Rows share width with gaps and stack on phones unless a phone direction is set. Boxes can also be grids (`display: grid`, `gridColumns` × `gridRows`, items with `colSpan`/`rowSpan`); grids are the main layout tool (structures in Add element are grids, `setGrid` adds or trims empty cells and never removes one with content), and on phones a grid is one column unless a phone column count is set.
- Every section is edited as a layout. `toLayout` in `apps/storefront/src/convert.ts` turns a built-in section into one: simple sections (announcement, card and list sections) become elements; the rest (order form, FAQ, reviews, gallery, countdown, contact, header, footer, …) become a block in a layout. New pages, templates and the editor's page load go through it, so sellers never see the old fixed sections. "Add section" offers only generic pieces (`sectionPresets` in `layout-tree.ts`: only the empty section); purpose-made pieces (order form, reviews, FAQ, …) are blocks added inside a section. A section is the page's top level: its panel is the container (name edited in the panel header, then Layout: content width, margin, padding; Style). Sections are listed by their seller-only `name` (preset or original section name when created; "Section N" when blank), never by their content. The ready-made pieces appear only in Add section; Add element offers elements, blocks and an empty box. Tree arrows only open and close (selection never does that), and selecting something opens the tree down to it. The renderer still draws typed sections, because blocks use them.
- A block's look settings are the `group: 'layout'` fields of its schema; the editor shows them at the top of the Style tab (`BlockStyleForm`), and the Content tab holds only its content. List items (every `list` field) are rows: drag handle (drag, or arrow keys), the item's icon, its title (click opens it), duplicate and delete.
- Icon list block: items are icon + one line of text + optional link (no heading); settings: vertical/horizontal, alignment, item and icon spacing, icon size and colour, text colour, dividers (style, width, colour); hover: icon and text colour per item. Block hover settings are named `<name>Hover<rest>` (iconHoverColor), shown under the Style tab's Hover state, fall back to the normal setting, and are drawn by the preview while Hover is being edited.
- The Hero banner block was retired: migration `0077_hero_to_image_text` turned saved hero sections and blocks into Image with text. The Text, Image, Image with text, Video, Call to action and Standalone icon blocks were retired too (Announcement keeps the shared call-to-action renderer): `retireOldBlocks` in `convert.ts` turns them into elements (a box keeping the block's id and style), run on saved pages by the data step in `apps/api/src/migrate.ts` (idempotent, ids deterministic so draft and published stay equal, revision bumped) and on imported files. Retire other old blocks the same way (rewrite saved pages to a kept type in a migration first, then delete the type), so no saved page ever holds a type `readContent` no longer knows.
- Add element lists Blocks (`currentBlocks` in `PageEditor.tsx`: icon list, Custom HTML) and, under Obsolete, every other older block until it is redone and moved up. Custom HTML (`html` block, `html` field kind) is stored exactly as the seller wrote it (HTML, `<style>`, scripts, outside libraries, forms; the seller is responsible for it) and is part of the live page as written; a page with one gets the open CSP (`openCsp` in `server.tsx`, chosen by `hasCustomHtml`), other pages keep the hash-only CSP. Platform safety rests on the dashboard being another origin: host-only session cookie and the API's origin check. It must never run in the dashboard: it is inserted into a page only when `ctx.live` is true, which only the storefront server sets; the editor preview draws it in place after DOMPurify (`previewHtml` in `PageEditor.tsx` via `ctx.previewHtml`: scripts, handlers, script URLs, frames removed; `<style>` kept; preview forms never submit), and any other render without that cleaner gets a scripts-off frame (`EmbedFrame`, `sandbox="allow-same-origin"` only). Never set `live` in the dashboard or insert the value into its DOM. Its https stylesheet links (`customHtmlCss`) are added to the preview document. It is stored as a length-checked string through parameterised queries and never evaluated on the server.
- Layout CSS weight: base rules in `layoutBaseCss` (and storefront rules that style layout nodes) weigh one class (put tags or extra classes in `:where()`), so the per-node `.n-<id>` rules, written later, always win.
- Order forms are found only through `orderBlocks()` (order sections and order blocks in visible layouts); the storefront's order handler and the page's default button link both use it.
- The editor's layout tools: structure tree under a layout section (drag to reorder or drop into a box), click in the preview to select any element, click a selected heading, text or button again to type on the page, Add element dialog (elements, blocks, ready-made layouts in `apps/dashboard/src/layout-tree.ts`). In the editor preview every box has a faint dashed outline, inset a little more per nesting level (no padding is added), so nesting stays visible. The hovered or selected box's solid outline and its handle sit at the box's real edge (outline just inside), so content never looks outside its box. Boxes and layout sections show a small handle in the preview that selects them (even when empty). Copy/paste (⌘C/⌘V, or the panel buttons) keeps a section or element in this browser's localStorage (`writeClip`/`readClip`), so it pastes into other pages too; the right-click menu's Paste style puts the copied item's desktop, phone and hover styles (and a block's look settings) onto an item of the same kind (same element kind and block type, or section on section), keeping its content; ⌘D and the tree's hover icon duplicate. Tree edits are the pure functions in `layout-tree.ts`; duplicates get fresh ids (`reId`), because ids must be unique on a page.
- Element panels have Content, Style and More tabs (More: layout, position, size, spacing, transition duration/easing, device visibility). Buttons have an icon position (before/after the text) and a Style › Background group: Classic (colour) or Gradient, from the same gradient settings as sections (`gradientLeaves` in `schema.ts`, `BackgroundTypeRow` and `GradientControls` in `SectionDesignControls.tsx`); element gradients merge phone and hover values with the desktop ones. Two-choice selects in content forms show as a joined-button switch. Buttons also have an attention animation on the More tab (pulse, shake, bounce, shimmer, glow; slow/normal/fast), rendered as `data-anim` attributes styled in `layoutBaseCss` and switched off under `prefers-reduced-motion`. Section style (`styleFields`): background is none, colour, gradient (two colours with positions 0–100%; linear with an angle, or radial with a shape and starting point; built only by `gradientCss` in `sections.tsx`), image (fit, position) or video (a direct https .mp4/.webm, muted and looping, with the image as poster), plus an overlay colour and strength for image and video; `SectionFrame` draws these as layers behind the section. Min height centres the content. Top and bottom spacing go to 300px. The storefront CSP allows `media-src https:` for background video.
- The editor is dark: `.editor` redefines the colour tokens, and dialogs opened from it follow. The preview iframe keeps the page's real colours.
- Images a page uses are kept in `page_media` (draft and published), which blocks deleting them.
- The storefront has no signed-in user and reads only through `storefront_page`, `storefront_media` and `storefront_products`. The order form is a plain HTML form; its small script only updates the shown total.

- New landing pages start blank or from a published demo (see Demos): the Create landing page dialog asks for the name and offers the demo gallery, plus an optional product that replaces the demo's products (`productId`, only with `demo`). The old ready-made templates (`campaigns.ts`) were removed; the create API refuses `template`. All created/duplicated/imported pages start unpublished.
- Export/import: the page list exports a page's draft and settings with its images' storage details as a file signed with a key derived from `COURIER_KEY` (`signExport`/`verifyExport` in `secrets.ts`); only unchanged signed files import. Import always creates a new unpublished page (page-limit lock, `readContent` and `checkReferences` as usual): images already in the store are kept, other platform images are copied in through `saveImage` (counting against storage), missing images and products the store lacks are blanked (`remap` in `pages.ts`).
- The page-list Duplicate action copies the saved draft into a separate page, including media references and SEO fields. Creation and duplication share the store page-limit lock. A copy must never change the source page or its published content.

## Orders

- Every order, from the storefront or typed in by the team, goes through `place_order_lines` (`place_order` is its one-product form, used by the storefront). It prices every line from its variant and delivery from the buyer's chosen option through `shipping_charge` (see Delivery options), takes stock and records the warehouse. All tracked lines ship from one warehouse, because cancels and returns put stock back into `orders.warehouse_id`. App code never sends an amount.
- Status changes go through `set_order_status`, which holds the allowed steps (new → confirmed/hold/cancelled, confirmed → packed, packed → courier, courier → delivered/returned). Cancelling or a return adds back what `order_items.stock_taken` says the sale took.
- Public forms carry a random checkout UUID. `place_checkout` serializes retries, calls `place_order` once, and records the number/total in tenant-scoped `checkout_receipts`. Reusing a completed token with different values is refused. Confirmation reads an opaque receipt through `storefront_receipt`, never an amount from the URL.
- Storefront orders are limited to 5 per phone per hour, and a hidden form field catches bots. Typed-in orders have no limit.

- Order filters and CSV export share `orderWhere` in `apps/api/src/order-query.ts` and the validated filter contract in `apps/storefront/src/order-filters.ts`. Dates are Bangladesh order-creation dates; end dates include the whole day. Status counts ignore the selected status but honor search/source/date filters.
- Saved order views belong to one member in one store and use `order_views` row-level security. Keep rolling periods relative rather than saving today's resolved dates. Enforce the 20-view limit under the per-member/store advisory lock.
- CSV exports include all matching orders up to 10,000, never just the loaded page or a silently truncated result. Quote CSV fields, neutralize formula-like text, preserve phone numbers as text, and omit buying prices. Abort stale browser exports when filters or stores change.

- Keep Orders compact: one toolbar for search and saved views, advanced filters in a dialog, and concise rows/cards. Do not show customer phone numbers under names in the order list; keep them in order details and retain phone search. Use actual scoped counts for summaries and label any QA preview data as sample.

## Sales tools

- Discounts (`discounts`, `discount_products`): amount off the order, amount off chosen products (percent, or a fixed amount per item), buy X get Y (value = percent off the cheapest qualifying items, 100 = free) and free delivery. Each is a code or automatic (no code, with a title shown on the order form via `storefront_offers`), with minimum amount or quantity, total use limit, once per phone, start/end dates and on/off.
- Only `discount_amount()` (migration 0075) works out what a discount takes off. `pick_discount()` gives each order one discount, the typed code or the best automatic one, whichever saves more, and counts its use in the statement that checks the limit. A typed code that does not apply is refused. `place_order` returns the order number and the total; show that total, never one worked out in app code.
- An empty product list means no products, never all: deleting a product can only narrow a discount. Order edits re-run the order's own discount on the new lines; a deleted discount keeps the agreed amount.
- Incomplete orders: the page script saves what a buyer typed once the phone is valid (`save_checkout_draft`), one row per number, swept after 90 days. Ordering marks it ordered.
- Fake-order protection: `blocked_phones` refuses storefront orders (typed-in orders still work). Repeat orders for the same product within 24 hours are marked, never refused.
- Repeat sales: buyers whose last order was delivered `days` ago and who have not ordered since; a logged call hides them for 7 days, or 90 if not interested.
- Profit (owners and admins only): delivered sales − buying price copied at sale (`order_item_costs`). Delivery charges go to the courier and are left out.
- Out of scope: expense tracking, team tasks, attendance and referral pages. We are not a bookkeeping, project or HR tool.
- Couriers: Steadfast logins are encrypted with `COURIER_KEY` (`apps/api/src/secrets.ts`) and never returned. Booking locks the order row so a double click cannot book twice. `STEADFAST_URL` points tests at a stand-in. Self delivery (`courier = 'self'`) is turned on in Settings › Couriers by owners and admins; sending an order that way records a shipment with no booking or tracking, and the team marks it delivered or returned by hand.
- Settings › Store is the business itself (name, logo, favicon, contact, address, optional registration), never online-store settings. The favicon is shared by every sales channel: the storefront serves it at `/favicon.ico` (`storefront_favicon`) and every page links there. Settings › Invoices holds what printed orders add; its header reads the Store details.
- Icon fields hold a library icon name or `media:<id>` (the seller's own PNG/JPG/SVG from the media gallery; `mediaIconId`/`isIconValue` in `icons/catalog.ts`). Own icons are page images in `references()` (so they cannot be deleted while used) and are drawn by `MarketingIcon` with the `image` lookup from `ctx`. SVG uploads are rasterised to WebP like every image; no SVG is served.
- Style presets live in `apps/storefront/src/themes.ts`; the storefront and the editor preview both apply them.
- Ad pixels are written into page scripts, so their IDs are format-checked in the API, the database and again before rendering. Each response's CSP allows its own inline scripts by hash.

## Demos (console)

- Landing pages, templates and single sections the Uddokta team designs with the normal page builder in an ordinary store (the demo store), then turns into demos on the console's Demos screen (`apps/console/server/demos.ts`, `pages/Demos.tsx`). A demo is a snapshot of the source's saved **draft**: `demo_items` (migration 0101) holds the content, its image details and where it came from. Its images are copied under the demo's own key prefix (`<demo id>/…`) at snapshot time, so the source can change or lose images without breaking a demo. "Update from source" takes a new snapshot (version + 1); stores that used it keep their copies. The New demo dialog loads the demo store and lists its landing pages and templates with their sections underneath; picking one row decides the kind (whole page, whole template, or one section). Thumbnails are uploaded from the administrator's computer (a form save: `data` JSON plus `thumbnail`), checked and converted by `processImage` (`apps/api/src/images.ts`, kept free of app imports so the console can load it); without one, the demo's first image is used. Nothing piles up in R2: `console_save_demo` (migration 0102) returns the demo's files before and after each save, and the console deletes the ones no longer used (a replaced or removed thumbnail, images a new snapshot dropped), only ever under the demo's own `<demo id>/` prefix; deleting a demo deletes all its files.
- Security: `demo_items` has no grant for the app role. Sellers read only published demos through `demo_list` / `demo_take` (definer functions, no content in the list); the console changes them only through `console_*` functions that check the administrator and write the audit log. A test proves a seller cannot read the table or call the console functions.
- Using a demo always copies it into the seller's store through `bringIn` in `apps/api/src/pages.ts` (shared with page import): images copied through `saveImage` (counting against storage), other stores' products and collections blanked (or products swapped for the seller's chosen one), another store's header/footer dropped, then `readContent`/`readTemplateContent`. Where sellers see them: Create landing page (`DemoGallery` in `NewCampaignDialog.tsx`), New template (demos of that type; owners and admins, checked before any image is copied), and the editor's Add section ("Ready-made sections", `POST /stores/:handle/demos/:id/section`, given fresh ids like a paste).
- Default templates for new stores: one published template demo per type can be the default (`demo_items.is_default`, migration 0103; Templates tab checklist and the row menu's "Make default for new stores"). A default stays published and cannot be deleted (database check `demo_items_default_published`, API 409 `demoDefaultLocked`); making another published demo of the type the default is the only way to change it, and the old one stays an ordinary demo. After a store is created, `applyDefaultTemplates` (`templates.ts`, via `demo_defaults()`) replaces its built-in copies with the defaults through `bringIn`; a type without a default, or any failure, keeps the code version in `builtInTemplates` (`site.ts`). Existing stores are never changed. To improve a default: edit it in the demo store, then Update from source.
- Section demos must pass `readContent` (no store-only blocks), so they work on landing pages and templates alike.
- Demos are saved page content: a migration that retires a block must rewrite `demo_items` too (the data step in `migrate.ts` does).
- The console service needs the R2 variables (it copies demo images).

## Templates (online store)

- Like Elementor Pro's Theme Builder: every part of the store is a **template** made in the page builder. Types (`templateTypes` in `apps/storefront/src/site.ts`): header, footer, home, product, collection, products (all), collections (all), page (store pages), cart, search, account, notFound. Each template is a row in `templates` (draft, published, revision, history like landing pages); `template_media` blocks deleting images in use.
- Each type has a **built-in template**: every store has its own copy as a `templates` row (`built_in`, one per type, made with the store by `builtInRows` and for older stores by the data step in `migrate.ts`, from `builtInTemplates` in code). Sellers edit it like any template; it is always published, never deleted (row-level security, API 409 `templateBuiltIn`), the flag never changes (trigger), and it does not count against the template limit. One published template per type can be the store's **default** (`is_default`, unique per type; a default cannot be unpublished). What the storefront draws (`storefront_template`, `templateOf` in `server.tsx`): the item's chosen template if published and of that type, else the default, else the built-in copy, else the code's built-in. Products, collections and store pages pick with `template_id` (the Template card; deleting the template sets it back to null). Landing pages (Page settings) and page templates, every type but header and footer (Template settings), pick a header and footer with `HeaderFooterFields` (`canvas.headerId`/`footerId`; blank = store default, None = canvas off; checked by the API to be this store's header/footer templates; `renderThemed` draws them). Header and footer templates never save a canvas.
- Template content is page `Content` validated by `readTemplateContent` (store blocks allowed); new templates start blank, from the built-in, from a ready-made start (`readyMade`) or as a copy. Owners and admins change templates; staff only look.
- The template editor (`pages/TemplateEditor.tsx`) is a `BuilderHost` of the shared `Builder`: page templates preview inside the store's default header and footer; product, collection and page templates preview with a store item picked in the top bar. Template settings: name, Make default, fonts, the template's CSS.
- **Site settings** (`stores.site_style`, `readSiteStyle`, on the Online store page, `pages/OnlineStore.tsx`): colours, fonts, corners, width and site CSS for every store page and landing page; until saved, the style preset in `stores.theme` applies. Never write these values into CSS except through `siteCss`/`siteFontsHref`.
- Themes (the earlier single-document design) were removed by migrations `0089`/`0090`; each store's live theme look became its Site settings.

## Online store preferences

- Store language (`stores.language`, bn or en, default bn; Online store page, saved with the preferences): the language of the store's own words (buttons, form labels, messages, digits) on every store page and landing page. Storefront strings are written as `tr(ctx.lang, ['বাংলা', 'English'])` beside each other (`apps/storefront/src/words.ts`, with `num` and `taka`); any new buyer-facing string needs both. `<html lang>` carries it so page scripts pick digits. The seller's own text is never translated; editor-only hints stay Bangla. Both languages with a buyer switch may come later.
- Online store preferences (on the Online store page; API `apps/api/src/preferences.ts`, owners and admins): home page title, description and share image (deferred key `stores_share_fk`, so it cannot be deleted while set), and an optional store password. Only its hash is kept (`hashPassword`); while set, every store page (templates) shows the password page and cart and product order posts redirect to `/password`; landing pages stay open. The buyer's cookie is a digest of the store and the password hash, so changing the password closes open visits.

## Store pages

- `store_pages` (title, handle, rich-text `body` cleaned by `cleanRichText` on save and again when drawn, `visible`, optional `publish_at`, `policy`, `template`, SEO, revision). Shown at `/:handle` inside the store layout when visible and due (`storefront_store_page`); landing pages win the address if both existed. Staff add and edit; owners and admins delete.
- Landing pages and store pages share one address space: `chooseHandle` in `pages.ts` (via `page_handle_free`) picks free handles for both, and the `check_page_handle` trigger on both tables refuses a clash (409 `pageHandleTaken`).
- Policies (refund, privacy, shipping, terms, contact), one of each per store, start hidden from our own Bangla drafts in `apps/api/src/policy-drafts.ts`; `/policies/:kind` redirects to the policy's page. The contact page also lists the Settings › Store contact details. Creating a page can append a link to the footer menu.

## Menus

- `menus` (store_id, handle, title, `items` jsonb tree, revision): any number per store, up to 30. `main-menu` and `footer` are made for every store by a trigger, cannot be deleted (row-level security) and keep their handles (API). Staff edit; owners and admins delete.
- Items are `{ id, title, link, children }`, at most 3 levels and 150 items, validated by `readMenuItems` in `apps/storefront/src/menus.ts` (shared by API, storefront and dashboard). Links to collections, products and pages hold the record's **id**; `resolveMenu` turns them into addresses when the page is drawn, so renames never break a menu. A link whose record is gone, a draft or unpublished is left out of the storefront and counted as broken in the dashboard (`storefront_link_targets`).
- Other links: home, all products (`/products`), all collections (`/collections`), web address (`/path` or https only), phone (`tel:`) and WhatsApp (`wa.me`). Saves send `revision`; a stale one gets 409 `menuChanged`.
- The storefront header draws `main-menu` (dropdowns and the phone menu are `<details>`, no JavaScript); while it is empty the header lists the store's collections. The footer draws `footer`. Tree edits in the dashboard are the pure functions in `apps/dashboard/src/menu-tree.ts`.

## Cart and search (online store)

- The cart is a cookie (`cart`, base64url JSON of `[variant id, quantity]`, at most 20 items, as `place_order_lines` caps storefront orders) with no prices in it; every view reads prices through `storefront_cart_lines`. `/cart/add`, `/cart/update` and `POST /cart` are plain forms (no JavaScript needed) and ignore posts from other sites (Origin check).
- `POST /cart` checks out through `place_cart_checkout` (receipt token, fingerprint, retries return the first receipt, as `place_checkout`), which calls `place_order_lines` with source `website`: the database prices lines, delivery and discount, takes stock and picks the warehouse. The cart empties on success and `/cart/thanks` shows the receipt. The cart page's script only updates the shown total for the chosen delivery option.
- The `cart` and `search` templates use the `cart` and `search` store blocks; the store header shows Search and Cart (with a count) links, and Product details can offer order now, cart, or both (`buyMode`).
- Side cart: when the store header's "Cart opens" setting is the drawer (default), the Cart link (`data-cart-drawer`) and every Add to cart form open a `<dialog>` drawer (`CartDrawer`/`CartDrawerBody`, `drawerScript` in `sections.tsx`, allowed by hash). The script posts the same `/cart/add` and `/cart/update` forms with `x-cart: drawer` and gets back the drawer's HTML drawn by the server (prices from `storefront_cart_lines`) plus `x-cart-count`; `GET /cart/drawer` opens it. Without the script, or on any failure, the forms and link go to the cart page as before. The drawer shows lines with quantity −/+, remove, subtotal, the nearest free-delivery amount (display only) and Checkout (the cart page). The header count counts only items still sold and cleans the cookie.
- `/search?q=` uses `storefront_search` (active products whose name, type, brand or a tag contain every word; ILIKE, Bangla-safe).

## Buyer accounts (online store)

- Buyers sign up and sign in with mobile number + password (`buyer_accounts`, one per number per store; migration `0093`). The number is **not verified** (no SMS yet), so an account sees only orders placed while signed in to it (`orders.buyer_account_id`, set by `storefront_link_order` from the checkout receipt), never other orders with the same number. Phone + SMS code can replace this once SMS exists.
- The app role has no access to `buyer_accounts`, `buyer_sessions` or `buyer_login_failures` (row-level security on, no policies, no grants): the storefront uses only the `storefront_buyer_*` functions, which take the store id from the server. A test proves the app role cannot read them.
- Sessions: a random token in the host-only `buyer` cookie (httpOnly, Lax), only its sha256 kept, 30 days. Five wrong passwords lock a number on a store for 15 minutes; unknown numbers are checked against `dummyHash`. Posts from other sites are ignored (`fromThisSite`); `next` must be a path on the store.
- Pages: `/account`, `/account/login`, `/account/register` (the `account` template type and Account block), `POST /account` (name, address), `POST /account/logout`. Saved name, phone and address prefill order and cart forms. The store header shows the link when its "Buyer account link" setting is on; menus can link to it.

## Delivery options

- `shipping_rates` replaces the old fixed inside/outside charges. A store has any number of options (name, area note, price, on/off, order), and buyers choose one on the order form. Orders keep `shipping_rate_id` and a copy of the name in `shipping_name`. Deleting an option leaves past orders as they were.
- Delivery is free when any of an option's conditions holds: products total (before coupon) ≥ `free_over`, item count ≥ `free_min_qty`, or the order includes a product in `shipping_rate_products`. Only `shipping_charge()` in the database decides. The storefront script and dashboard previews repeat the rule for display only.
- Store creation asks for the inside/outside Dhaka charges and turns them into the first two options; Settings › Delivery manages them. The API refuses to turn off or delete the last active option. Owners and admins edit; staff read.
- Editing an order keeps its agreed charge on the same option unless the free conditions change; another option is priced afresh.

## Notifications

- The bell sits beside the logo in the sidebar and at the end of the phone top bar. Its panel opens what each notification is about, and Settings › Notifications holds the choices.
- Only database triggers create notifications, through `notify()` in migration `0065`. Never insert them from app code: storefront and courier paths must be covered too. The person who caused an event is never notified about it.
- `data` is a snapshot (number, name, product), so text reads the same later. New kinds need the check constraints, `notification_default()`, the kind lists in `schema.ts` and `components/Notifications.tsx`, text in `describe()` and a test.
- Incomplete orders are announced only after 15 minutes left open, because every storefront order saves a draft first.
- Browser pop-ups and sound are per device (`localStorage`); what a member receives is per store (`notification_settings`).

## Design rules

- Do not use the Hallmark skill or its linter in this project.
- Blend of Shopify's admin and a modern analytics dashboard. From Shopify: black frame and sidebar, rounded content panel, dense tables with a filter bar. From the dashboard: large page title with a one-line description, green primary and active state, a stat row with sparklines and charts on Home.
- Our own code, name and logo. Never Shopify's logo, assets or copy.
- Neutrals plus one green; other colours only for status badges and errors. 14px body text, thin borders, fully round (pill) controls, 12px cards. Boxes that hold several lines, lists or pictures keep soft corners (`--radius-box`, `--radius-media`).
- Lists use the one data table (`.data-list`, `.filter-bar`, `.data-table`; see the comment in `app.css`). One value per cell: phone, email, address and links get their own columns; only phones stack them. Bulk actions use `components/Selection.tsx`.
- Standard input field: the `.input` class. White, 32px, thin `--color-rule-strong` border, pill-shaped with 12px side padding, 13px text, no shadow, and a green outline on focus.
- Small controls by default: buttons and inputs are 32px with 13px text. Sign-in forms use 40px.
- Mobile components should be more compact than their desktop equivalents, following the page editor: reduce 16px text to 14px and 14px text to 13px, with tighter line spacing and padding. Use 32px buttons with 13px text and compact 32–36px icon buttons and list controls. Keep related actions on one row where they fit; icon-only buttons need accessible labels. Editable inputs keep 16px text (to avoid iPhone focus zoom) at 36px height; buttons stay 32px. Never add per-page overrides to undo the global mobile sizes. Apply these sizes to the dashboard controls; the storefront preview must retain the storefront's own responsive styles.
- Buttons: white ones have a thin edge and a soft drop shadow; filled ones (primary, danger) have a top-to-bottom sheen in the brand colour with a light top edge and a soft shadow, and look pressed in when clicked. Shadows come from tokens.
- Dialogs are native `<dialog>` (`.modal` centred, `.picker` a floating side sheet, `.drawer` the phone menu) and animate both in and out. Build them from `components/DialogHead.tsx` (title and round close button), `.dialog__body` and `.dialog__foot`; a dialog's own class sets only its width and inner layout. Edge-to-edge choices use `.dialog-list`. Close them only through `useDialog` in `components/dialog.ts`: `close()`, or `close(then)` for actions like Done. Its props close on a backdrop click (sent as a cancel, so a dialog's own `onCancel` guard still applies). Never unmount them directly, or the exit animation is skipped.
- Page editor section settings use the same scale as the rest of the dashboard: `.input`, `.input-affix` and `.btn` for fields, 13px labels, 28px segmented toggles, tokens only (see the "Section settings" block at the end of `app.css`). Do not add one-off pixel sizes or hex colours there. The builder's settings panels are the one exception to pill controls: they use 4px corners, joined segment buttons and Elementor-style joined spacing fields (four sides plus a link button, side names underneath), in our colours.
- Charts are inline SVG with no chart library. Never invent figures: sample data is labelled as sample.
- Colours, spacing and type come from tokens, never one-off values.
- Bangla is chosen and tested first; English fits around it.
- Plain seller language. Every empty state says what to do next.
- Status badges and Soon tags are small uppercase pills (Bangla keeps a readable size, it has no capitals).
- Colours are picked with `components/ColorPicker.tsx` (area, hue, opacity, one row of 9 recently used colours kept per browser), used through `ColorControl`, which opens it in a browser popover anchored to the field with a small pointer at the swatch. A colour joins Recent when its popover closes or when it is pasted into the HEX field (applied whole, # optional), never while dragging; use it for any new colour field. Colours are `#RRGGBB` or `#RRGGBBAA` when see-through, and the schema accepts only those.
- **Never:** gradients other than the filled-button sheen and the colour picker's own hue/opacity/area fills and the Gradient background-type icon, emoji icons, stat cards beyond one row, decorative glass or glow effects, or anything that reads as generic AI output.
